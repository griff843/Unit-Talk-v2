## The defect, reproduced rather than read

The `SNAPSHOT_REMOTE` heredoc was extracted from the workflow and executed against a
temporary host directory, with `.unit-talk-release` deliberately left un-advanced between
runs — the state a deploy that dies after the env writes actually leaves.

Against the previous `deploy.yml`, two distinct failures were observed:

```
overwrite:  snapshot for the running release contained
            "ALLOWED_CAPPER_EMAILS=NEW-SHAPE-ADMITS-NOBODY\n"  (the failed deploy's value)
prune:      ENOENT — .env.smart-form.e48106fc… did not exist at all,
            evicted by the mtime-ordered prune after 8 newer snapshots
```

Against this head, both are preserved.

## Why this matters to Milestone 1

`ALLOWED_CAPPER_EMAILS` is validated non-empty at three layers and shape-validated at none;
the `smart-form` healthcheck is `curl -fsS localhost:4400/login`, which returns 200 with an
allow-list that admits nobody; `deploy.yml` is the only writer of `.env.smart-form`. A
wrongly-shaped value therefore ships green, and configuration rollback is the way back.
The documented recovery — edit the secret, re-dispatch the same release — is exactly the
same-tag redeploy that M2 covers.

## Independent review

Reviewed adversarially by an independent reviewer at `9e296e6c5`, which returned five
findings. Three were accepted and fixed in `f1681e6e0`: the same-tag redeploy staleness
(now M2), the stale "five bounds credential copies" comment (the exemption sits outside the

A second independent round re-attacked the reworked fix at `f1681e6e0`, specifically the
marker lifecycle, `$GITHUB_RUN_ID` availability, and whether any mutation passes. It
enumerated every failure point in the job and found **no live defect**, and it reproduced
the four-control battery independently with the same isolation result — each mutation
failing only its own two named tests and nothing else.

Two of its observations are recorded because they bound what this proof claims:

- The marker is cleared on the line *before* `docker compose pull`, so a container-runtime
  failure after the release record advances does not re-raise it. That is deliberate: the
  marker's only job is to flag disagreement between the on-disk configuration and the
  release record, and that disagreement is resolved exactly where the record advances.
- The structural marker test asserts that the raise appears in the snapshot body and that
  the release step clears it *after* advancing the record. It does **not** assert the
  intra-step ordering of the raise relative to the `INFLIGHT` read. A future edit that moved
  the read below the write would make every run see `INFLIGHT=1` — but that is mutation M2's
  exact signature and is caught by the functional refresh tests, so the pair has no blind
  spot. The structural test alone is weaker than its name implies; that is stated here
  rather than left for a later reader to discover.

Neither round found a defect in the engineering at `f1681e6e0`.
