## Findings (code and production, read-only, 2026-11-08)

Code findings:
- `apps/smart-form/app/submit/components/BetForm.tsx:1572`: for a team sport the setup choice "Manual entry" sets `identityMode = 'structured-fallback'` (canonical teams), not `'manual'`.
- `BetForm.tsx:2173`: `identityMode !== 'manual' && player-prop && !selectedPlayerId` refuses with "Select a player from the results". That is the observed blocker.
- `BetForm.tsx:1042`: `identityMode = 'manual'` is reachable only when BOTH team searches returned `not-found` (`canUseManualIdentity`).
- Server contract (`apps/api/src/smart-form-validation.ts`): the `manual` resolution is all-or-nothing. Every entered participant must have `canonicalParticipantId = null`; each entered name is checked with `findCanonicalCoverage`, and a name that resolves canonically is refused ("claims a canonical coverage gap, but ... resolves to canonical participant"). For team sports at least two entered participants are required.
- Consequence: for Celtics @ Bucks both teams are canonical, so the manual path refuses (team names are covered); the structured-fallback path requires a canonical player (`validateSearchBackedPlayer`, ~line 478). **No existing contract admits canonical teams plus an uncovered player.** The client guard is correct against the current server contract; the defect is a missing tier in the resolution ladder, not a one-line client bug. Removing the client guard alone would produce a server 400.

Production observation (read-only SQL on `public.participants`): no row matches `%herro%`, `%burries%` or `%dulcich%` in any sport. These are genuine sport-wide coverage gaps, not stale team assignments.

## Objective

Add one explicit, server-verified tier to the participant-resolution ladder: **structured team fallback (canonical away/home/team ids, `eventId: null`, team sports only) + one manually entered player**, recorded truthfully as a manual player coverage gap. Align client and API. Preserve Track Only; make manual-player picks Track Only only.

## Bounded implementation packet

Contract (`packages/contracts/src/smart-form.ts`): on `CanonicalParticipantResolution` add an optional `manualPlayer` as a sibling of `player`, mutually exclusive with it:
`manualPlayer?: { displayName: string; canonicalParticipantId: null; reason: 'canonical-coverage-gap' } | null`.

Server (`apps/api/src/smart-form-validation.ts`), only on the structured-fallback outcome (`eventId` null, `TEAM_SPORTS`):
1. Reject `manualPlayer` together with `player`, with any `eventId`, or in non-team sports.
2. The two sides and the selected team are verified exactly as today (canonical, same sport, selected team is one side).
3. Verify the coverage claim against reference data the server reads itself: `referenceData.searchPlayers(sportId, name, 25)` and the existing alias/confusable folding (`foldConfusables`, `aliasKey`, Latin-only rule). If any result alias-matches the entered name, refuse ("claims a coverage gap but resolves to canonical player X; use the canonical selection"). If the search itself throws or times out, fail as a retryable error and never record a gap (apps/smart-form/CLAUDE.md: a failed search is not a coverage gap).
4. Flat metadata must carry no canonical `playerId` for a manual player; the persisted pick metadata records player provenance `manual-coverage-gap` and makes no provider-verified or CLV claim (manual-fallback picks are labeled, per the standing hold).
5. Fail closed on delivery: a submission with `manualPlayer` is accepted only as Track Only. `distributionMode: 'delivery-eligible'` with `manualPlayer` is refused with an explicit reason, whatever the allow-list says. This is a new guard and gets a mutation check. `TRACK_ONLY_INTENT_GUARD` and `SMART_FORM_HTTP_CONTRACT_GUARD` are not weakened; edits to `apps/api/src/handlers/submit-pick.ts` are permitted only if the new refusal cannot live in validation.

Client (`BetForm.tsx`, `lib/form-utils.ts`; `lib/form-schema.ts` only if the schema needs the field):
6. When identity mode is structured-fallback, the market is `player-prop`, and the player search has returned a definitive not-found (not an error, not idle), show an explicit "Player not found: enter manually" control, labelled honestly (saved as a manual entry without provider verification; Track Only).
7. In that state the submit guard at `BetForm.tsx:2173` accepts a typed name and `buildParticipantResolution` emits canonical teams plus `manualPlayer`. A search that errored or never ran keeps the current refusal ("Typing a name is not enough").
8. The submission guards in `lib/form-utils.ts` (`evaluateSubmissionGuards`) mirror the server rules, each stated once next to the server rule it mirrors, including the Track Only-only rule.
9. The receipt and slip show the player as manually entered, never as canonical or verified.

## Acceptance Criteria

- A player prop for a canonical-team matchup with an uncovered player (Herro and Burries shapes, NBA, Celtics @ Bucks) can be submitted through the form as Track Only, persists, and the receipt shows the player as manually entered.
- The same works for an NFL shape (Dulcich, Lions @ Dolphins), a sport with no player coverage at all.
- The server refuses a manual-player claim when the entered name resolves to a canonical player in that sport, with a reason naming the canonical match.
- The server never records a coverage gap when the player search errors or times out; the submission fails retryably.
- `manualPlayer` with `player`, with an `eventId`, in a non-team sport, or with a non-null canonical id is refused.
- A `delivery-eligible` request carrying `manualPlayer` is refused, whether or not the capper is on the delivery allow-list; Track Only is never widened, and no delivery record is created.
- Teams stay canonical: the persisted pick carries real away/home/team participant ids and no canonical player id; provenance is `manual-coverage-gap`, with no provider-verified or CLV claim.
- The client guard still refuses a typed player name when the search errored or has not run; it relaxes only after a definitive not-found.
- Existing paths are unchanged: canonical+event, structured fallback with a canonical player, and all-manual (teams uncovered) keep their current behavior and tests.
- No reference-data population, no provider or ingestion change, no production DDL or data write, no kill-switch or delivery change.
