### CLI contract

```
pnpm results:odds-api-scores --league <NFL|NBA|NHL|MLB> [--days-from 1|2|3] \
     (--fixture <path> | --live) [--apply]
```

- Default is dry-run through `createDryRunIngestorRepositoryBundle`; output is the JSON blast-radius report plus the per-event decision list.
- `--fixture` reads a file and makes no network call. `--live` requires `ODDS_API_KEY` and is the only path that contacts the vendor. Exactly one of the two is required; neither is a default.
- `--apply` writes. The CLI refuses `--apply` when the configured Supabase project ref is production (`zfzdnfwdarxucxtaojxm`) and exits non-zero before any read or write. No override flag in this phase.
- All arguments are validated together before any work, and one message lists every problem with the full corrected invocation.
- Every run, dry or applied, prints credits used and remaining (null for fixtures). Applied runs open a `system_runs` row with `run_type='odds-api-scores.operator-run'`, opened as failed and upgraded on completion.

### Parser: an event is `final` only when all hold

1. `completed === true`.
2. `scores` is an array of exactly two entries whose `name` values equal `home_team` and `away_team` exactly, one each.
3. Both `score` strings match `^\d+$`.
4. `last_update` is a valid timestamp, later than `commence_time`, and not in the future.
5. `now - last_update >= 15 minutes` (settle delay).
6. `id` is 32 characters and `sport_key` equals the requested league's key.
7. Tie rule: equal scores are accepted only for NFL. Equal scores in NHL, NBA or MLB are rejected as `tie_not_possible`.

Anything else is `not_final` (clean pre-game or live shape) or `rejected` with a named reason. Rejected and not-final events write no results.

### Resolver

- Teams: both must resolve through the static table to exactly one `participants` row of type `team` in that sport; otherwise skip the event (`team_unmapped`).
- Foreign-event guard: if an event with a different provenance (`sgo`, `operator-manual-entry`, anything not `odds-api`) exists for the same two teams on the same Eastern date, skip (`ambiguous_existing_event`). No odds-api row is ever written onto another provider's event, and no second event is created beside it.
- Start-time guard: if the event already exists and the stored `starts_at` differs from `commence_time` by more than 6 hours, skip (`commence_time_changed`).
- Event row: `external_id` = vendor `id` unchanged; `event_name` = `"{away display_name} @ {home display_name}"` from canonical participants; `event_date` = Eastern date of `commence_time`; `status='completed'` only for a `final` parse; roles `home` and `away` in `event_participants`. A `completed` event is never regressed by a later non-final response.
- Event metadata: `{ source: 'odds-api', providerKey: 'odds-api', ingestionSource: 'odds-api-scores.operator-run', ingestionCycleRunId, starts_at, sport_key, home_team_name, away_team_name, resultsProof: { matchMethod: 'static-team-map', providerEventId, providerLastUpdate, fetchedAt, completedObserved: true, payloadKind: 'live' | 'fixture-doc-derived' | 'fixture-recorded' } }`.
- Results, `source: 'odds-api'`, written only on `final`: `game_total_ou` (participant null, home + away); `team_total_ou` (home; away; that team's score); `game_spread_margin` (home; away; own minus opponent); `game_moneyline_win` (home; away; 1 / 0, or 0.5 each on an NFL tie). No other key is ever written; no period, regulation or 3-way key.
- Existing truth (amended by step 13): a `game_results` row from any other source under one of these keys skips the event's results (`results_already_present`). Existing `odds-api` rows are reconciled against the seven expected rows: a complete identical set on a completed event with its `resultsProof` is an idempotent skip (`results_already_present`, zero writes); any mismatched value, `sourced_at` or unexpected row is `conflicting_results` with zero writes; a partial identical set is completed. An event is marked `completed` with `resultsProof` only after all seven rows are confirmed durable. The CLI never reads or writes `settlement_records` or `picks`.
