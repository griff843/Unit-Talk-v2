# WORK-2026111104 — Active-lane discovery: recognize WORK-### lane branches (proposal)

Tier: T2 · Lane type: governance · Executor: claude

Repo-owned work order (tracker independence, ratified 2026-09-05). No Linear issue exists for this identity by design.

## Authority

- PM-directed finding, 2026-11-11: `resolveActiveLaneManifests` in `scripts/ops/shared.ts` skips every open PR whose branch name carries no UTV2-/UNI- issue id (reason "branch name carries no UTV2-/UNI- issue id"). This covers every `WORK-###` lane branch.
- Evidence: on `main` `152e48527`, 11 of 20 open PRs are on `<owner>/work-<n>-<slug>` branches (for example #1842 `claude/work-2026110804-lean-mode`, whose manifest `docs/06_status/lanes/WORK-2026110804.json` exists at its head). None of them reaches `activeManifestOverlap` in `ops:lane-start`; their file locks are enforced only by the local lease registry and local manifests of the checkout that started them.
- WORK-2026102903 deliberately left `issueIdFromBranchName` unchanged ("also used by open-PR lock discovery, which this lane deliberately does not change"). This lane is that change.
- This touches the lane/dispatch system, which is a PM architecture decision. It is a proposal PR on its own, not bundled, and is not merged without PM approval.

## Objective

Make open-PR lane discovery recognize `WORK-###` lane branches so a remote `WORK-###` lane's file locks are visible to `ops:lane-start`, with the same fail-closed behaviour UTV2/UNI lanes already get.

## Acceptance Criteria

- A test in `scripts/ops/shared.test.ts` that fails on `main` shows an open `WORK-###` PR whose manifest exists only at its head is invisible to `resolveActiveLaneManifests` and therefore to `activeManifestOverlap`.
- `issueIdFromBranchName` derives its namespaces from `ISSUE_ID_NAMESPACES` (UTV2, UNI, WORK), so the two cannot drift again.
- After the fix the same test passes: the WORK lane is discovered from its PR head and its lock overlaps a conflicting scope.
- Fail-closed: a manifest read that throws for a `WORK-###` branch raises `ActiveLaneDiscoveryError`, exactly as for UTV2/UNI (covered by a test).
- Non-lane branches (`main`, `dependabot/...`, `claude/readiness-contract-measurement`) still resolve to `null`.
- `pnpm lint`, `pnpm type-check` and `pnpm test` exit 0.
