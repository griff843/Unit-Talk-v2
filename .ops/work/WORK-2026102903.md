# WORK-2026102903 — Bind lane PRs for WORK-### lanes

Tier: T1
Lane type: governance
Executor: claude

Source: PM operating-model directive (2026-10-29), priority 3: lane admission, proof and closeout defects that materially affect engineering throughput. Mechanical tier floor is T1 (`.github/workflows/**` is a tier-c prefix); the tier is not lowered.

## Objective

`.github/workflows/lane-pr-binding.yml` resolves the lane from the PR branch with `grep -oiE 'utv2-[0-9]+'`, so a `WORK-###` lane (the repo-minted namespace in `ISSUE_ID_NAMESPACES`) never has `pr_url` bound when its PR opens. Its post-merge closeout then fails with "Cannot resolve authoritative merge SHA: manifest.pr_url is missing or invalid", the lane stays active on a merged branch, and `MERGED_PR_ACTIVE_LANE` hard-fails every other lane-start until someone repairs it. 7 of the last 21 failed `post-merge-lane-close.yml` runs (2026-10-18 to 2026-10-28) failed this way.

Widen the branch match to the `UTV2|UNI|WORK` namespaces and pass the resolved issue id to `lane-link-pr.ts` explicitly with `--issue`, so the trusted binder does not depend on `issueIdFromBranchName` (UTV2/UNI only; also used by open-PR lock discovery, which this lane deliberately does not change).

## Acceptance Criteria

- The workflow's "Resolve lane from branch" step yields `bind=true` and `issue_id=WORK-<n>` for a `<owner>/work-<n>-<slug>` branch whose registered manifest names that branch, and still yields `bind=false` for a branch with no work identifier, a missing manifest, or a manifest registered to a different branch.
- `lane-link-pr.ts --issue WORK-<n> --branch <owner>/work-<n>-<slug> --base main --pr <url> --github-event` binds the lane and transitions it to `in_review`.
- Both are covered by executed tests in `scripts/ops/lane-link-pr.test.ts`; the existing workflow-shape tests stay green.
- No change to permissions, triggers, checkout refs, the trusted-code split, the persist/retry step, merge-gate, ERV, P0 Protocol or `issueIdFromBranchName`.
