## Measured problem (read-only, 2026-11-07 ~04:50Z, `main` `ff9c4b595`)

- **No index leads with `updated_at`** on production (`zfzdnfwdarxucxtaojxm`, 107,851 picks, 10 indexes) or staging (`xskgrzbteyqdufktjrjx`, 201,551 picks, 18 indexes).
- **The two guard statements that #1832 added to `listByLifecycleStates` (`packages/db/src/runtime-repositories.ts`) scan the whole table.**
  - Watermark W: `select updated_at from picks order by updated_at desc limit 1`. This is a seq scan plus a top-N sort.
    - Production: 50 ms.
    - Staging: 1,665 ms with only one client connected, all buffers shared hit.
  - Check 2: a HEAD `count` with `updated_at > W and created_at <= last` and no status filter. This is a seq scan.
    - Production: about 35–94 ms.
    - Staging: 197 ms to 1.3 s at idle, and 8.4 s and 11.7 s in slow phases.
- **Statement timeouts.** The authenticator `statement_timeout` is 8 s on both databases. The staging Postgres log shows 5 statement timeouts (57014) in 24 h, and all of them were these two statements: 16:52:39, 18:23:45, 18:23:54, 18:24:04 and 18:35:53Z on 2026-11-06.
- **`updated_at` changes on every update.** `picks_set_updated_at` (BEFORE UPDATE, every row) rewrites `updated_at` on each update, so every update to an indexed row becomes non-HOT. Staging HOT is already only 13.5% (21,478 of 159,021 updates).
- **The ledger matches.** Production `supabase_migrations.schema_migrations` has 139 rows (max `20261010170100`), and `supabase/migrations/` has 139 files. The staging ledger has 5 rows and is not used for applies there.

## Objective

Add one plain b-tree index, `public.picks_updated_at_idx ON public.picks (updated_at)`, as a reversible, fail-closed migration, with staging before-and-after proof.

Do not change application code, the population guard, statement timeouts or any other object.

## Acceptance Criteria

1. **Migration `supabase/migrations/20261107060000_utv2_1981_picks_updated_at_idx.sql`.**
   - **Fail-closed precondition.** Declare `-- FAIL-CLOSED-PRECONDITION: public.picks_updated_at_idx`. The guard is a `DO` block that runs before any DDL.
     - If `to_regclass('public.picks_updated_at_idx')` is not null, the object must be all of the following, or the block raises SQLSTATE `42P07`:
       - an index on `public.picks`;
       - access method `btree`;
       - exactly one key column, `updated_at`;
       - no predicate and no expression;
       - `pg_index.indisvalid` and `indisready` both true.
     - This turns two hazards into refusals: an INVALID index left by a failed `CREATE INDEX CONCURRENTLY` (which `IF NOT EXISTS` would otherwise skip silently, and which parity cannot see), and a same-named object of another shape.
   - **Index statement.** Then `CREATE INDEX IF NOT EXISTS picks_updated_at_idx ON public.picks (updated_at);`.
   - **No `CONCURRENTLY` in the repo file.** No live migration uses it, and whether the Supabase CLI apply path runs a migration file inside a transaction is unverified.
   - **Header comment.** The header must say that production gets the index first, out of band, by `CREATE INDEX CONCURRENTLY` under Griff's separate authorization. After that the file is a validated no-op, and the guard confirms the out-of-band index is valid.
2. **Down script `db/migrations-rollback/20261107060000_utv2_1981_picks_updated_at_idx.down.sql`:** `DROP INDEX IF EXISTS public.picks_updated_at_idx;`. It is executable and survives the reversibility round trip (up, down, up gives an identical schema hash).
3. **`migration-reversibility-gate.yml` passes at the implementation commit:**
   - down-script presence;
   - the precondition drill, where the decoy is refused with 42P07, the schema fingerprint is byte-identical and an empty-scratch case is included;
   - the schema round trip.
   - Prove, rather than assume, that the guard refuses a name that exists but is not valid. In scratch Postgres, show that it refuses:
     - an INVALID same-named index (for example, `pg_index.indisvalid` forced false);
     - a same-named index on another column;
     - a partial same-named index.
     It must also accept a valid matching index as a no-op.
   - If the drill tooling cannot express these cases, record them as a scratch-database transcript in the proof, with the exact commands and SQLSTATEs. Do not modify the drill or gate.
4. **Live Schema Parity fails on the PR because production lacks the index. That is expected.**
   - Record it as `PENDING_POST_DEPLOY` per `scripts/ops/proof-schema.ts`: `observed_result: FAIL`, the exact run and job, `production_ddl_applied: false`, `required_phase: post-deploy-before-lane-close`.
   - Do not add `--allow-drift` or edit any gate.
5. **Proof order.**
   - The `migration` proof profile needs four receipts, each `{result, run, job}`, at `verified_source_sha` (the last non-proof commit): `precondition_drill`, `schema_roundtrip_drill`, `writable_db_proof_staging` and `live_schema_parity`.
   - Push the implementation commit alone first, harvest the receipts at that SHA, then commit the proof as a proof-only commit.
   - `verification.md` keeps `MERGE_SHA: pending merge` for proof-binding-validator, and the executor result points at `diff-summary.md`.
6. **Staging evidence, with the verification boundary stated explicitly.**
   - Before: read-only `EXPLAIN (ANALYZE, BUFFERS)` of the two exact statements, with timings and the plan nodes.
   - After: the same statements once staging has the index, with expected plans of an Index Only Scan Backward for W and an index range scan for check 2.
     - Staging apply is the exact SQL, run out of band by Operating Claude under PM authorization, with `ci.yml` idle.
     - Then verify `indisvalid`/`indisready` and the index size.
   - Load: the PR's first CI run is the under-load before sample, and the next lane CI run after the staging apply is the after sample. Record the guard statement timings from the job log.
   - Write overhead:
     - insert and update cost before and after (`pg_stat_statements` deltas or a bounded timing probe);
     - the HOT ratio before and after (`n_tup_hot_upd/n_tup_upd`);
     - index count and size.
   - Mark anything not measured as not proven. Do not claim that the index ends staging slow phases: indexed readers have reached 7.7–7.8 s in `pg_stat_statements`.
7. **Production authorization packet** at `docs/06_status/proof/UTV2-1981/production-apply-packet.md`. It is a draft for Griff, and nothing in it is executed. It covers:
   - the exact `CREATE INDEX CONCURRENTLY IF NOT EXISTS` statement, with `set lock_timeout` and `statement_timeout` settings for the session;
   - preconditions: an `indisvalid`/`indisready` check that the name is absent, active sessions and long transactions, and disk;
   - expected duration and size from the staging build, scaled to production;
   - lock behavior: CIC takes SHARE UPDATE EXCLUSIVE, waits for older transactions, and cannot run in a transaction block;
   - failure handling: an INVALID index is dropped with `DROP INDEX CONCURRENTLY IF EXISTS` and the build retried;
   - post-apply verification: `pg_index` validity, EXPLAIN of both statements, then `supabase db push` so the repo file runs as a guarded no-op and the ledger records it, then Production Post-Migration Verification and Live Schema Parity PASS;
   - rollback: `DROP INDEX CONCURRENTLY IF EXISTS`;
   - the ordering consequence: merge, then Griff's production apply, then parity PASS, then lane close.
8. **No other changes.** No application, test-behavior, timeout or guard change. `database.types.ts` does not change, because an index has no type surface; confirm that.
